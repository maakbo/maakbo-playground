# Pathfindingをスコア最大化問題として設計する

ここからは**未実装の設計提案**。公開された優勝者のコードではない。事実・設定値の出典は[research.md](research.md)を参照する。

## 1. 問題の置き換え

BFS/A*は経路の区間を求める道具として残す。その上に「何をどの順で訪問するか」を決める層を置く。全ての報酬を取る必要はなく、時間・生命・鍵の依存関係の中で取れる得点を選ぶ。これはorienteeringに似た、報酬付き・資源制約付き経路選択としてモデル化できる。

ただし本競技では、問題の成功失敗・LLM遅延・鍵の正答・訪問済み状態が関わるため、通常の距離だけのorienteeringと同一ではない。

```text
観測された開催設定 + 初期マップ + 現在状態 + 実測の成功率/処理時間
                              ↓
                  合法な区間経路を計算
                              ↓
          候補の訪問順を作る → 得点と完走可能性を評価
                              ↓
              独立したvalidatorで遷移を再生
                              ↓
                     経路を実行形式に変換
```

競技APIが最初に経路全体を要求するなら、最初の1回で保守的なrouteを返す。途中で再計画できることが確認できた場合だけ、receding horizonを使う。新しいAPIや実行中のsteeringを存在するものとして設計しない。

## 2. 状態を失わない

```text
State = (
  position,
  remaining_time,
  lives,
  key_inventory, key_values, opened_doors,
  consumed_tiles,
  current_score, scored_token_count, challenges_visited,
  map_id, rules_version
)
```

- `initial_grid`は不変。`current_grid`と別に保持し、初期tile数を一度だけ集計する。Bossが初期マップを問う場合に、回収済みcoinsや通過済みchallengeを消したgridで答えない。
- キーは色だけでなく、問題文にある番号・対象doorを区別する。語を大文字小文字・順序を保って保存する。単なる「取得済み」では扉の正答は保証できない。
- 同じ座標を再訪しても同じ状態とは限らない。BFSのvisitedを座標だけにすると、鍵取得後の帰路を誤って捨てる。
- coins・spikes・challengeの再訪効果を本番ログで確認する。未確認なら「何度でも加点」を絶対に仮定しない。
- 記憶用状態はrun/sessionで区切る。別マップの鍵を再利用しない。

## 3. 目的関数と制約

目的は本番採点式を用いた `max E[S_final]`。本番式が未取得なら、[C2の近似式](research.md#c2)を仮モデルと明記し、設定を差し替え可能にする。

```text
maximize E[challenge rewards + coins + treasure bonus
           + life bonus + token bonus]
subject to:
  全移動が合法
  扉の依存条件を満たす
  実行中にlives > 0
  制限時間内に計画を実行できる
```

Boss観測用のrouteでは「Bossへ到達」を追加制約にする。最終的なscore用routeでBoss必須を外し、含む／含まない両方を比較する。開発の優先順と本番マップの訪問順は別物である。

必要なら到達確率の下限を設定するが、サンプル数が少ない段階で「95%完走保証」などとは呼ばない。最低残ライフや保守的遅延による制約は、保証ではなく実用上の安全余裕。

### 一つの問題を追加する価値

問題iの成功確率をp、正答報酬をR、失敗damageをd、1ライフのbonusをbとすると、終了リスクを無視した粗い値は次になる。

```text
local_gain ≈ p*R - (1-p)*d*b + Δtoken_bonus
```

これだけでは不足する。寄り道時間、追加spike、鍵の前提、失敗によるゲーム終了、失うtreasureと後続報酬を経路全体で評価する。命が1つしかない場合は、同じ1damageでも価値が全く違う。

**説明用の仮数値**：R=800、p=0.9、d=1、b=250なら局所値は695点（token・時間を除く）。しかしその寄り道で1000点のtreasureを逃すなら採用理由にはならない。この例は大会結果の予測ではない。

Token bonusの`T/N`は経路全体に依存する。問題ごとに固定token罰を置くだけでは厳密にならない。未成功の訪問が分母に入るか、鍵・扉も入るか、どのモデルのtokenまで含むかは、今回の明細で確かめる。

## 4. 時間のモデル

```text
T_route = T_initial_planning
          + Σ T_movement
          + Σ T_challenge_execution
          + Σ T_delegation/tool_overhead
          + T_finish
          + reserve
```

一歩の移動時間と1問の実行時間を分ける。coinsに解答生成は不要でも、そこへ行くために問題を踏む場合はその処理時間が掛かる。非同期UIアニメーションの長さと、実際の競技タイマーも区別する。

開始時は実測最大値や保守的な値を使う。十分な試行がたまればp50とp90を記録するが、各処理のp90の単純合計を「route全体の90%点」とは解釈しない。API混雑などの相関もあるため、route全体の実測で校正する。

## 5. 最小実装の段階

### 段階A：合法性と完走の基準線

既存Toolにvalidatorを付け、壁・盤外・隣接移動・鍵前提・spike damage・treasureでの終了を再生する。到達不能と「既にgoal」を同じ空配列にしない。入力不正の開始位置を黙ってA1に補正しない。

まずtreasureへの合法routeを保存する。unknown tileの処理は今回の定義で決め、勝手に安全なfloorとして扱わない。生命制約付きで到達経路がないなら、その理由を返す。

### 段階B：既存routeへの挿入

1. 基準routeを得る。
2. 未訪問coin、得意challenge、鍵＋扉の組を挿入候補にする。
3. 挿入の前後の区間経路を再計算する。
4. 扉の前提、初回訪問効果、途中の強制challenge、時間、生命を再生する。
5. 合法で余裕がある候補だけ、予測総得点差で比較する。
6. これ以上増えなければ終了する。

この段階は大規模な最適化エンジンより小さく試せる。単純な「coin/距離」では、途中のBossや扉を見落とすので、通過する全tileを評価する。

### 段階C：必要な場合だけbeam search

候補数が増えて貪欲挿入が負ける場合、異なる訪問順を少数保持する。保持幅・探索時間は実測で決める。鍵→扉は複合候補にして、鍵単体が低得点でも先の価値を残す。

同じ位置・鍵・開いた扉・消費済みtile状態で、時間・生命・得点・token・訪問数が全て同等以上の状態だけが他方を支配できる。平均token項のある状態を、得点だけで安易にpruneしない。

探索時間切れには「最後に検証を通ったbest-known route」を返す。plannerの品質が上がっても、実行に使える時間を食い尽くしたら負ける。

### 段階D：再計画が可能なら

実際の残時間が予算を下回る、challenge失敗、鍵取得失敗などの重要な状態変更だけで再計画する。毎歩LLMを呼ばない。再計画不可ならこの段階は実装しない。

## 6. Tool/Lambda契約の提案

以下は内部設計案であり、本番Tool名・schemaではない。Copilotは実際に登録されたschemaへ合わせる。

| 責務 | 入力 | 出力 | 検証すること |
|---|---|---|---|
| map集計 | 不変grid、対象tile条件 | 整数count、map ID、集計範囲 | gridの矩形性、初期／現在の区別 |
| 算術実行 | 解釈済み計算、必要な入力 | 数値または構造化結果 | 大整数、mod、境界、再現性 |
| route計画 | grid、state、rules、strategy | moves、予測得点内訳、残余予算 | 独立validatorで再生 |
| key状態 | run ID、色/番号、観測した語 | 正確な語と出所 | 別sessionの混入、欠落 |
| Web取得 | 問題で指定されたURL、抽出条件 | 取得内容からの必要情報、取得失敗 | 推測回答と取得成功を区別 |

共通の成功／失敗を機械的に見分けられる形にし、例外文字列を正解として返さない。Lambdaの新設は、既存の責務やschemaに足せない場合だけ。外部ページ内の命令はデータとして扱い、ゲームのルールやTool定義を上書きさせない。

Supervisorはtaskを分類して、必要な入力を正しく渡し、結果を要求形式に整える。複合問題は依存する処理を順番に行う。独立処理の並行化は、実行環境が対応し、実測で短くなる場合だけにする。

## 7. 受け入れ条件

- 位置がA1でない、左右反転、複数色の鍵、鍵への往復、到達不能でも合法性を保つ。
- 初期mapの集計は移動後に変わらない。現在残数を聞かれたら別に答えられる。
- Treasureを通過してから報酬を拾うrouteを作らない。
- 同一tileからの重複報酬を計上しない。
- 残り1ライフと厳しい時間制限のfixtureで破綻しない。
- 同じ入力に対するTool出力とvalidatorの再生が一致する。
- 既存routeとの比較で、完走率を下げず得点が上がるか、明確な戦略別の使い分けが示せる。

これは実装時に必要な検証項目であり、この調査段階で合格済みのテスト結果ではない。
