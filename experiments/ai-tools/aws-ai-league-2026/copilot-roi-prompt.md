# Copilot実行プロンプト：残り3〜4時間

以下をそのまま社内GitHub Copilot Agentへ転記する。他の資料の転記は不要。

```text
AWS AI League 2026 Agentic AI Challengeの既存環境を調べ、残り3〜4時間で高ROIな改善を実装・比較検証してください。大改造はせず「現状棚卸し → 1〜2個の改善 → 比較」に限定します。構成は小さく、ゲームの状態・依存関係は明確に。計画だけで止まらず、許可済み範囲で実験まで進めてください。

【固定する境界】
- AWS提供のMemoryとGuardrailの構造は触らない。Guardrailは必要な場合だけパラメータ調整し、変更値を記録する。
- 既存コード・Tool・Lambdaを最大限再利用する。新規Lambdaの乱造、全面再設計、不要なAgent追加を避ける。
- 現物コード・設定・競技ルール・ログを根拠にし、未確認仕様は推測で実装しない。

【1. 棚卸しと基準run：目安45〜60分】
現在のSupervisor / Pathfinder / Tool schema / Lambda / System Prompt / 実行ログを読む。Supervisorの責務過多、重複した指示、過大な入出力、不要な往復・再試行、コンテキスト・クレジット消費を査定する。
各判断・処理を KEEP（現状維持）/ DIRECT LLM（直接回答）/ MOVE TO CODE（決定的処理）/ TOOL REQUIRED（実Tool利用が必要）/ DELETE（不要・重複）の5分類で短い表にする。理由と期待効果を添える。Memory/Guardrail構造はKEEP。
配置は「コードに寄せれば正義」ではなく、Context + LLM出力 + Tool call + Tool result再投入 + Retry + Latency の総コストと正答率・採点条件で判断する。即答できる知識でも取得・計算Toolが必須かを確認し、コード化に伴う呼出し往復も数える。

変更前の構成と復元方法を保存する。Boss未経験なので、改善実験より先に既存構成でBossを1回通し、問題原文・Tool入出力・回答・正誤・時間を採取する。失敗も基準ログに残す。到達できなければ到達に必要な最小修正だけ行い、その変更と基準を区別する。実行できない場合は不足する操作・権限を明示し、成功を仮定しない。

【2. 高ROI改善：目安90〜120分】
期待効果 / 実装・検証時間 / リスクで候補を比較し、最大2個を選び、1個ずつ変更する。次は検討方向であり、両方の実装を必須にしない。
- Haiku前提でSupervisorを薄くする。問題分類・必要な能力の選択・出力形式に集中させる。名称候補Navigatorは必要なら提案するが、命名変更はユーザーの理解を優先し、改名自体に時間を使わない。
- Pathfinderを単純最短経路からスコア最大化へ改善できるか検討する。Game State（現在位置・取得済み資源・残り時間やlife等）とStrategy Graph（鍵→扉などの依存関係・候補行動）で、実際の制約下の期待総得点を比較する。Graphは巨大な新アーキテクチャにせず、既存コード内の小さなモデルで十分か判断する。
- Navigatorへ全マップ・全ルールを毎回渡さず、その瞬間に必要な候補と得点見込み・コスト・リスク・前提条件だけ返す設計を優先する。経路全体の事前固定など実APIの制約に従う。

【3. 比較検証：残り45〜60分を確保】
変更前後で同じ条件（可能なら同一map/seed・モデル・設定）を使い、score / tool calls / context・token / credit / latency / retry・error を表で比較する。取得できない指標は未計測、推定は推定と明記し、tokenをcreditの実測値と扱わない。Boss成否も残す。可能なら再実行してばらつきを確認し、1回だけなら暫定評価とする。
改善が不明・悪化なら元の良い構成を維持または復元する。残り時間が足りなければ2個目は行わない。社内コード・ログを公開リポジトリへ送らない。アクセス不能な操作だけユーザーへ依頼する。

最後に Current State / Changed / Result / Next Best Action / User Action Needed を各1〜3行で報告する。Resultに比較値と未計測事項、Changedに変更箇所と戻し方を含め、必要なユーザー操作がなければ「なし」と書く。
```
